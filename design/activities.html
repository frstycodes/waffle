How it works

What Waffle would have to build, from Discord's developer docs, the Embedded App SDK's source and the Discord desktop app on this Mac. Read before deciding: the last part is the risk.

The app is a web pageServed from https://<app id>.discordsays.com with frame_id, instance_id, platform, channel_id, guild_id in the URL. Discord's proxy fronts its servers.
The client hosts itDiscord desktop puts it in a sandboxed iframe (scripts, same-origin, forms, popups, pointer lock) inside a native view layered over the window, then moves and clips that view to whatever slot the app is in: focused, grid tile, corner, pop-out.
A postMessage bridgeThe app's SDK sends [opcode, payload] messages: a handshake, then commands (authorize, get the channel, set activity, open link, invite dialog, purchase…) and events the client pushes (who's in it, who's speaking, layout mode). The client answers each one.
Discord's serversStarting or joining runs the app's entry-point command (or the older POST /activities/{channel}/{app}); leaving is POST …/instances/{id}/leave. The gateway sends instance updates, and guilds carry activity_instances. These come from unofficial docs, not verified.

Spike, Nov 22: a non-Discord host can run an activityA bare macOS web view framed Putt Party from 945737671223947305.discordsays.com and played the SDK's host. Putt Party loaded, handshook and asked to authorize, with the host page's origin either "null" or the activity's own (the SDK allows both); discordsays.com sends no frame-ancestors or X-Frame-Options. Authorizing as the user worked: POST /oauth2/authorize returned a code once it was a user install (integration_type: 1; a server install needs a server). Putt Party's own server then refused the code with 404 for the made-up instance_id, so the last piece is a real instance from Discord's launch call while in voice. That's ordinary client work, not a wall.
